## 1. Introducción

Este documento fija la **pila tecnológica y la línea base** de la app móvil de QuickBite, que
migra de React Native a **Flutter**. El documento 07 describe la arquitectura conceptual de la
app móvil (alcance por perfiles, capas, repositorios, navegación, estrategia de datos, seguridad
y pruebas) y sigue siendo válido como modelo mental: este documento **traduce cada decisión de
herramienta a su equivalente en Flutter** y especifica el alcance de la primera entrega
incremental (base del proyecto, autenticación y catálogo).

### 1.1 Por qué Flutter

- El panel de administración ya está consolidado (React + Vite + TypeScript) y la API está
  estable; la app móvil se reconstruye sobre Flutter para obtener tipado estático en toda la
  cadena, un único lenguaje (Dart) y soporte multiplataforma.
- La coherencia del stack se mantiene: un solo lenguaje de interfaz para admin y móvil sobre el
  mismo contrato REST (documento 04).

## 3. Correcciones al contrato asumido

La petición inicial nombraba el catálogo como `/api/v1/catalog`. El contrato real (documento 04 y
`admin/openapi/swagger.json`) es:

| Recurso | Endpoint real | Anotación |
| :--- | :--- | :--- |
| Auth | `POST /api/v1/auth/register`, `/login`, `/refresh`, `/logout`, `/forgot-password`, `/reset-password` | Coincide con lo asumido |
| Categorías | `GET /api/v1/categories` | **No** existe `/api/v1/catalog/categories` |
| Productos | `GET /api/v1/products` | **No** existe `/api/v1/catalog/products` |
| Detalle | `GET /api/v1/products/{id}` | |
| Opciones | `GET /api/v1/products/{id}/options` | |

Esta entrega consume `/api/v1/products` y `/api/v1/categories`.

## 4. Objetivo

Entregar el proyecto Flutter inicializado, con la arquitectura base completa, el flujo de
autenticación (login y registro) funcional contra la API real y la pantalla principal de catálogo
funcional, lista para que las siguientes entregas (carrito, pedidos, perfil, repartidor) se
añadan como features sin refactor de la base.

**Público objetivo:** cliente autenticado. El repartidor y el administrador quedan fuera de esta
entrega (el administrador se gestiona desde el panel web, documento 08).

## 7. Estilo de código

- **Clean Architecture** por feature: `data` (DTOs + datasource + implementación de repositorio),
  `domain` (entidad + interfaz de repositorio), `presentation` (providers + widgets).
- **DTOs con `json_serializable`**, entidades de dominio con `Equatable`; mapeo explícito
  `dto → entity` en el datasource (nunca se expone el DTO a la presentación).
- **Inyección de dependencias por constructor** en datasource y repositorios; los providers de
  Riverpod son el único punto que instancia la cadena.
- **Errores tipados con `Result` implícito**: los repositorios lanzan `AppException` ( subtypes de
  documento 07 §13.1); la presentación los convierte en mensajes con `errorMessage()`.
- **Inmutabilidad** en entidades y providers.
- **Sin lógica de negocio en widgets**: los widgets pintan; los providers deciden.
- **Comentarios:** ninguno innecesario; el código se explica solo.

Ejemplo de la convención de repositorio:

```dart
abstract class AuthRepository {
  Future<AuthSession> login({required String email, required String password});
  Future<AuthSession> register({required RegisterRequestDto request});
  Future<void> logout({required String refreshToken});
  Future<AuthTokens> refresh({required String refreshToken});
}

class AuthRepositoryImpl implements AuthRepository {
  AuthRepositoryImpl(this._remote, this._tokens);
  final AuthRemoteDataSource _remote;
  final TokenStorage _tokens;

  @override
  Future<AuthSession> login({required String email, required String password}) async {
    final dto = await _remote.login(email: email, password: password);
    return dto.toEntity();
  }
}
```

## 8. Estrategia de pruebas

| Tipo | Herramienta | Alcance |
| :--- | :--- | :--- |
| Unitarias | `flutter_test` | Mapeo de errores, validadores, formatters de moneda, DTOs (`fromJson` con JSON real) |
| Repositorios | `flutter_test` + `dio` con `HttpClientAdapter` falso | Params de query, cabecera `Authorization`, persistencia de tokens, logout |
| Interceptor | `flutter_test` + `Dio` real con adapter falso | Añade `Bearer`, detecta 401, refresca una sola vez, no entra en bucle, reintenta la petición original |
| Widgets | `flutter_test` | Login, Registro, Home: render de estados (carga/vacío/error) y validaciones |
| Integración | `integration_test` | Flujo login → home (requiere dispositivo; fuera de CI actual) |

**Ubicación:** los tests conviven junto al código como `*_test.dart` en `test/`, replicando la
estructura de `lib/`.

**Cobertura objetivo:** ≥ 70 % en la capa de lógica de negocio (documento 07 §16). En esta
entrega el foco es `core/` y `features/*/data`.

**Regla TDD:** todo test se escribe antes de la implementación y debe fallar por la razón
correcta antes de pasar.

## 12. Desajustes de serialización documentados

Flutter usa `snake_case`; la API serializa en `camelCase` (verificado en
`admin/openapi/swagger.json`). Se respeta la API:

| Endpoint | Desajuste | Tratamiento |
| :--- | :--- | :--- |
| `GET /api/v1/products` | Backend lee `categoriaId`, `precioMin`, `precioMax` | Se envían esos nombres exactos |
| `POST /api/v1/auth/login` | Body `email`, `password` (camelCase snake_case-free) | Sin impacto |
| `POST /api/v1/auth/register` | Body `nombre`, `email`, `password`, `telefono`, `rol` | Sin impacto |
| `POST /api/v1/auth/login` (respuesta) | `accessToken`, `refreshToken`, `expiresIn`, `user` | Sin impacto |
| `POST /api/v1/auth/register` (respuesta) | `creado_en` (`JsonPropertyName` explícito) | El cliente mapea `creado_en` |
| Errores de validación | `details` es un mapa `propiedad → string[]` | `error_mapper` lo convierte a `AppException` con mensajes por campo |
| Errores de negocio | Envelope `{timestamp, status, error, message, path, details}` | Se toma `message` |
