# Database Model - QuickBite v1.0

**Version:** 4.1 | **Date:** 2026-09-14 | **Status:** Approved

---

## 1. Purpose and Scope

This document defines the canonical relational model for QuickBite v1.0. The model is implemented on **PostgreSQL 15 managed by Supabase** and is synchronized with the EF Core backend according to decision `05#D-10`.

QuickBite is intentionally **single-branch**. The database has one catalog, one inventory, one configuration set, and one global administrator role. It does not contain `branches` tables, `branch_id` columns, or marketplace relationships.

### 1.1 Functional groups

| Group | Tables |
|---|---|
| Identity and access | `usuarios`, `direcciones`, `repartidores`, `tokens_refresco`, `tokens_recuperacion_password`, `notificaciones`, `auditoria_acciones`, `dispositivos_push` |
| Catalog and inventory | `categorias`, `productos`, `producto_precios_historicos`, `inventario`, `producto_opciones` |
| Cart | `carritos`, `carrito_items`, `carrito_item_opciones` |
| Orders | `pedidos`, `pedido_items`, `pedido_item_opciones`, `pedido_historial_estados` |
| Configuration | `configuracion_sistema`, `metodos_pago` |

---

## 2. Modeling Principles

| Principle | Application |
|---|---|
| **Third normal form** | Entities are normalized to avoid duplicated operational data. |
| **UUID primary keys** | All public identifiers use PostgreSQL UUIDs generated by `gen_random_uuid()`. |
| **Immutable order data** | Order items, prices, options, and delivery addresses are snapshotted at order creation. |
| **Critical integrity in PostgreSQL** | Stock, order transitions, numbering, and delivery counters are enforced by triggers. |
| **Logical deletion** | Products and categories are disabled rather than physically deleted. |
| **Auditable changes** | Price changes, order transitions, assignments, cancellations, and critical operations are recorded. |
| **No push integration** | `dispositivos_push` remains in the schema but is not mapped, populated, or referenced by the application. |
| **No branch tenancy** | No branch fields or tenant filters exist in v1.0. |

## 4. Entity Relationship Model

### 4.1 Main relationships

| Origin | Destination | Cardinality | Description |
|---|---|---:|---|
| `usuarios` | `direcciones` | 1:N | A customer owns multiple delivery addresses. |
| `usuarios` | `repartidores` | 1:1 | Only users with the delivery-person role have an extension record. |
| `usuarios` | `tokens_refresco` | 1:N | A user can have multiple active refresh sessions. |
| `usuarios` | `tokens_recuperacion_password` | 1:N | Password-reset tokens. |
| `usuarios` | `notificaciones` | 1:N | In-app notifications. |
| `usuarios` | `auditoria_acciones` | 1:N | Critical actions attributed to a user. |
| `usuarios` | `carritos` | 1:1 | One active cart per customer. |
| `usuarios` | `pedidos` | 1:N | Orders placed by a customer. |
| `repartidores` | `pedidos` | 1:N | Orders assigned to a delivery person. |
| `categorias` | `productos` | 1:N | Products in a category. |
| `productos` | `producto_precios_historicos` | 1:N | Price history. |
| `productos` | `inventario` | 1:1 | Current stock for a product. |
| `productos` | `producto_opciones` | 1:N | Configurable product options. |
| `carritos` | `carrito_items` | 1:N | Items in a cart. |
| `carrito_items` | `carrito_item_opciones` | 1:N | Options selected for a cart item. |
| `pedidos` | `pedido_items` | 1:N | Items in an order. |
| `pedido_items` | `pedido_item_opciones` | 1:N | Historical options for an order item. |
| `pedidos` | `pedido_historial_estados` | 1:N | State-transition audit trail. |
| `pedidos` | `notificaciones` | 1:N | Order-related notifications. |

### 4.2 Important invariants

- A user can have only one default address.
- A product has at most one inventory row.
- A cart is unique per user and normally has one active state.
- Order numbers are unique and generated as `QB-YYYYMMDD-XXXXX`.
- An order can only transition through the allowed state graph.
- Stock cannot become negative.
- A delivery person cannot be marked available while holding an in-transit order.
- An order retains its delivery-address snapshot after the source address is edited or deleted.

## 7. Functions and Triggers

### 7.1 Timestamp functions

`set_actualizado_en()` updates `actualizado_en` on users, products, orders, and system configuration.

### 7.2 Order lifecycle

- `validar_transicion_pedido()` enforces the allowed state graph and populates state timestamps.
- `registrar_historial_pedido()` records insertions and state changes.
- `generar_numero_pedido()` creates a unique readable order number.
- `validar_stock_pedido()` rejects confirmation when stock is insufficient.
- `descontar_stock_pedido()` deducts stock when an order is confirmed.
- `restaurar_stock_pedido()` restores stock when an order is canceled.
- `incrementar_entregas_repartidor()` increments the delivery counter and releases the delivery person on delivery.
- `validar_transicion_repartidor()` prevents a delivery person with an in-transit order from becoming available.

### 7.3 Other integrity functions

- `validar_rol_repartidor()` requires the referenced user to have role `repartidor`.
- `actualizar_carrito_acceso()` refreshes cart access and expiration timestamps.

## 9. Migration and Deployment Rules

1. The existing Supabase schema is the source of truth for tables, triggers, functions, and views.
2. EF Core migrations must not attempt to recreate existing objects (`05#D-10`).
3. Recommended synchronization is a **baseline migration** marked as applied, or inverse scaffolding with migrations disabled.
4. Triggers, functions, and views are maintained in versioned SQL scripts outside EF Core migrations.
5. Database backups must include schema objects and seed data.
6. Every change to a critical trigger requires an integration test against a PostgreSQL container with the real schema.
