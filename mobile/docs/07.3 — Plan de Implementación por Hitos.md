## 1. Introducción

Este documento fija el **orden de ejecución** de la app móvil de Flutter de QuickBite. No
introduce requisitos nuevos: traduce a cortes de trabajo verticales el inventario de pantallas
del documento 07.1 y la línea base técnica del documento 07.2.

**Estado del backend verificado al redactar este documento:** los siete controladores que
consume la app móvil están completos (Auth, Catalog, Cart, Orders, Delivery, Notifications,
Users). Salvo la disponibilidad del repartidor (§4, decisión 2), todo el trabajo pendiente es
de frontend.

## 5. Orden de ataque

```
H0 (riesgo)  →  H1 (barato, desbloquea salida)  →  H2  →  H3 (núcleo)
   ↓                                                                      ↓
H4 (polling)  ←  ───  se cruzan cliente y repartidor  ───→  H7
   ↓
H5 (16 pantallas, mecánicas)  →  H6  →  H8 (release)
```

**H0.1 y H0.2 van primero** porque son baratos y eliminan el riesgo que arrastra todo lo demás.
**H3 antes que H4** porque el checkout es el flujo de revenue; **H5 antes que H7** porque 16
pantallas casi todas locales son cortes mecánicos de bajo riesgo que se absorben rápido, y H7
es el último bloque grande.

## 6. Fuera de alcance

No tocar el backend salvo `delivery/availability`: los otros seis controladores están completos.
No tocar la capa `core` existente (`dio_client`, `error_mapper`, `token_storage`, tema): H0.1 y
H0.3 solo la extienden. No introducir `drift` para caché de red más allá del historial de
búsquedas: D-13 es lo único que exige persistencia local en v1.0. Sin i18n, sin push, sin pago
real, sin multi-sucursal (D-01, D-08, D-09, RNF-07.4).

## 7. Verificación por hito

Cada corte se cierra con, desde `mobile/`:

```bash
flutter analyze
flutter test
flutter build apk --debug
```

Los comandos del documento de skills para móvil (`npm run lint`, `npm test`) están obsoletos:
la app migró a Flutter y los comandos vigentes son los tres anteriores.

### 7.1 Pruebas de flujo (H8.2)

`integration_test/` monta la app real y solo falsea el transporte HTTP, así que
cubre el cableado completo (providers, guard por rol, interceptor de sesión,
repositorios y pantallas) en vez de una pantalla suelta.

Con un dispositivo o emulador conectado se ejecutan como cualquier otra suite:

```bash
flutter test integration_test/<archivo>.dart -d <device-id>
```

Sin dispositivo, el objetivo headless `flutter-tester` las corre igual:

```bash
flutter test -d flutter-tester integration_test/cliente_flow_test.dart
```

**Un archivo por invocación.** `flutter-tester` lanza un proceso por suite y el
segundo falla con `Failed to launch mobile: The log reader failed unexpectedly`
—es una limitación del runner, no de las pruebas—, así que hay que pasar un
archivo cada vez (o apuntar a un emulador real, que sí las encadena).
