# 07.5 — Selección de Ubicación en Mapa y Geocoding Inverso

> **Estado: BORRADOR — pendiente de validación humana (Fase 1 de `spec-driven-development`).**
> Specs relacionados: `07.4 — Google Maps y Ubicacion Delivery.md` (delivery),
> `07.1` (pantallas SCR-CART-04 / SCR-PROF-07), `03 — Modelo de Datos`,
> `04 — Contrato de API REST`, `13 — Manual de Usuario`.

## 1. Objetivo

Permitir al cliente agregar/editar una dirección de entrega seleccionando la ubicación en un
mapa interactivo (pin central fijo), obteniendo coordenadas exactas y una dirección
autocompletada por geocoding inverso, manteniendo la edición manual. Persistir esas
coordenadas en la dirección **y en la orden**, para que el repartidor pueda abrir la
ubicación exacta en Google Maps / Waze.

Usuarios: **cliente** (selección y edición de dirección), **repartidor** (consumo de
coordenadas en la orden).

## 3. SUPUESTOS (validar antes de PLAN)

1. **Mapa: `google_maps_flutter` (ya en `pubspec.yaml:49`), no `flutter_map`.** El pedido
   dice "flutter_map o Google Maps SDK según la configuración del proyecto": la config
   existente es Google Maps (widget `DeliveryMap`, API key Android vía env `MAPS_API_KEY`).
   Así no se añade dependencia de mapa nueva.
2. **Geocoding inverso con el paquete `geocoding`** (usa el Geocoder nativo de Android; sin
   API key ni coste; iOS está fuera de alcance porque no existe carpeta `mobile/ios/`).
   Alternativa descartada: Nominatim HTTP (rate limit + User-Agent obligatorio) y Google
   Geocoding API (requiere billing).
3. **Persistencia en la orden: copia server-side.** `POST /orders` sigue enviando solo
   `direccionId`/`direccionSnapshot`; al crear, el backend copia `Latitud/Longitud` desde la
   dirección elegida (snapshot en el momento del pedido). Sin cambios de contrato en la
   request. Si la dirección no tiene coords → la orden queda con coords null (fallback
   textual, comportamiento actual).
4. **Nueva migración EF en `pedidos`: `latitud`/`longitud` `numeric(10,7) NULL`** (misma
   precisión que `direcciones`). Cambio de BD — requiere aprobación.
5. **Contrato API: aditivo.** `OrderDetailResponse` añade `latitud`/`longitud` (nullables).
   No se rompe nada existente.
6. **PUT de dirección mantiene la semántica actual** (`UserService`: solo actualiza coords
   si `!= null`; no se permite limpiar enviando null). Se documenta en el spec 04.
7. **El autocompletado rellena `calle` y `ciudad`** con la sugerencia del geocoder;
   `numero`, `referencia` y `alias` siguen siendo 100 % manuales. El usuario puede sobreecribir
   cualquier campo sugerido.
8. **Alcance UI:** `SelectLocationMapScreen` se integra en `AddressFormScreen`
   (SCR-PROF-07 / SCR-CART-04) vía botón "Ubicar en el mapa"; se reutiliza desde checkout
   porque el checkout delega en `/addresses/new`.
9. **En el móvil NO se cambia `CreateOrderRequestDto`**: las coords viajan por el backend
   desde la dirección (supuesto 3).
10. **`order-coords-usage` incluye**: (a) `order_detail_screen` usa coords reales del
    detalle (hoy hardcodeadas + TODO en `:149`), (b) `active_delivery_screen` hace lo propio,
    (c) botón "Abrir en Google Maps / Waze" con `url_launcher` (ya en pubspec) en detalle de
    pedido del repartidor. Si algún punto sobra, eliminar del alcance.

# FASE 2 — PLAN DE IMPLEMENTACIÓN (validado: 10/10 supuestos aprobados)

## P1. Flujo de datos objetivo

```
Cliente (AddressFormScreen)
  └─ "Ubicar en el mapa" → SelectLocationMapScreen (google_maps_flutter + pin fijo)
        ├─ onCameraMove   → LocationMapController.centro (estado, sin geocoding)
        ├─ onCameraIdle   → ReverseGeocodingService (paquete `geocoding`, Geocoder Android)
        │                     └─ sugerencia {calle, ciudad} → autocompleta form (editable)
        ├─ botón GPS      → LocationPermissionService (reutiliza delivery) + Geolocator
        └─ pop(LatLng)    → form actualiza controladores lat/lng (campos manuales siguen)
POST /orders  (sin cambios de payload: solo direccionId + snapshot)
  └─ OrderService.CreateAsync → _uow.Addresses.GetByIdAsync(direccionId)
                                  └─ copia Latitud/Longitud a la Order (snapshot server-side)
GET /orders/{id}        → OrderDetailResponse +Latitud/Longitud (nullable, aditivo)
GET /delivery/active    → OrderResponse           +Latitud/Longitud (nullable, aditivo)
Cliente detalle pedido  → mapa destino real + botones "Google Maps" / "Waze" (url_launcher)
Repartidor entrega activa → ídem
```

## P2. Decisión derivada de los puntos 5 + 10 aprobados

- `OrderItemResponse` **no existe**: los items son `IReadOnlyList<string>` (nombres).
  Las coords van en **`OrderDetailResponse`** (cliente) y, para que la pantalla del
  repartidor pueda usarlas, en **`OrderResponse`** (la respuesta compartida que devuelven
  `GET /orders`, `GET /delivery/available|active|history`). Ambos cambios **aditivos**
  (nullables). `PedidoEntrega` y `OrderDetailDto` del móvil ganan `latitud/longitud`.
- Origen del mapa (restaurante QuickBite Centro) sigue hardcodeado: es conocimiento del
  cliente, no de la API. El destino pasa a ser real; la polyline se elimina (lista vacía).

## P4. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| `GoogleMap` no es testeable en `flutter_test` (platform view) | Seam: provider `mapViewBuilder` por defecto construye `GoogleMap`; los tests lo sustituyen por un `SizedBox` que dispara callbacks. Toda la lógica vive en `LocationMapController` (unit-testeable). |
| `OrderResponse`/`OrderDetailResponse` son records posicionales → añadir params rompe compilación en todos los sitios de construcción | B4 los actualiza de una vez (OrderService, DeliveryService, tests); el fallo de compilación es el RED de TDD. |
| Geocoder nativo sin red/emulador sin servicio | El servicio devuelve `null` y la UI lo comunica sin bloquear; el form sigue siendo editable a mano. |
| Migración EF: snapshot/regeneración | `dotnet ef migrations add AddOrderCoordinates` desde `backend/` (`-p src/QuickBite.Infrastructure -s src/QuickBite.Api`); si falta la tool: `dotnet tool install --global dotnet-ef` (no tocar el código a mano del snapshot salvo conflictos). |
| Ejecutar en dispositivo requiere `MAPS_API_KEY` (env) | Afecta solo a runs en dispositivo; `flutter test` no lo necesita. |
| Semántica PUT coords null (punto 6) | Sin cambio de código: `UserService` ya solo actualiza si `!= null`; se añade test que lo fije + se documenta en spec 04. |
